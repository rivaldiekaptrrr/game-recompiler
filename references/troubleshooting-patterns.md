# Common Troubleshooting Patterns in Xbox Static Recompilation

This reference documents the most common failure modes and battle-tested solutions encountered when porting original Xbox games.

---

## 1. Unresolved Indirect Call (`[ICALL] Failed to resolve VA 0x...`)

### Symptom:
Console log prints:
```text
[ICALL] Failed to resolve VA 0x00201954 from caller sub_00123450
```
Followed by an immediate crash or null-pointer dereference.

### Cause:
The game called a function through a function pointer or C++ virtual method table (vtable). Static disassembly did not find a direct `CALL` instruction to this address, so the lifter never generated C code for it.

### Fix:
1. Extract the missing VA and add it to `config/seed_functions.json`:
   ```bash
   python -m tools.seed_from_log logs/run.log game/default.xbe \
       --functions tools/disasm/output/functions.json \
       --seeds config/seed_functions.json
   ```
2. Re-run `tools.disasm` with `--seed-functions config/seed_functions.json`.
3. Re-run `tools.func_id`, `tools.abi_analysis`, and `tools.recomp`.
4. Rebuild.

## 2. Audio Init Hang (DSP Command Doorbell)

### Symptom:
Game hangs at S2 during audio initialization. Watchdog triggers with thread spinning in DirectSound code.

### Cause:
Xbox DirectSound passes a command block to the DSP processor, sets a command bit, and spins until the DSP writes `0` back to indicate completion. In static recompilation, the DSP is not actively simulated by default.

### Fix:
Acknowledge the doorbell automatically in the APU hook:
- Identify the GP scratch memory page address (via `GPSADDR` scatter-gather table, usually offset `0x810`).
- Immediately clear the command word back to `0` upon receipt, or set environment variable:
  `RECOMP_APU_DSP_ACK=<address>`

## 3. GPU Pushbuffer Fence Spin (`D3DDevice_MakeSpace`)

### Symptom:
Game hangs with callstack inside `sub_XXXXXXXX` (D3D8 pushbuffer allocator), spinning on `Put - *GetPtr`.

### Cause:
Real NV2A hardware executes the pushbuffer in parallel and advances `*GetPtr`. In recompilation, pushbuffers are consumed synchronously at submit/flip time. If the game waits for `GetPtr` to move before writing more commands, it deadlocks.

### Fix:
Mirror the `Put` pointer into `*GetPtr` on every tick:
```c
xbox_Nv2aMirrorFence(g_pDevice_va, offset_Put, offset_GetPtr);
```

## 4. Arithmetic Errors / Silent Nan / Corrupted Logic (64-Bit Divides)

### Symptom:
Game does not crash, but calculations produce nonsensical results, matrices collapse to NaN, or timers jump wildly.

### Cause:
MSVC 64-bit integer divide helpers (`_alldiv`, `_aulldiv`, `_allrem`, `_aullrem`) rely on the x86 `rcr` (rotate through carry) instruction. If the lifter drops `rcr` or miscalculates multi-word shifts, operations where the divisor > $2^{32}$ fail silently.

### Fix:
- Add a runtime self-test in `main.c` (`recomp_selftest()`) that exercises the divide helpers with a 64-bit divisor ($0x100000007$) against known answers.
- If incorrect, override the math helper functions in `src/recomp_manual.c` with native C 64-bit integer arithmetic (`dividend / divisor`).

## 5. Corrupted Vtable / Wild Pointer at High VA (`0xFFFFFE00` or `0xFFFFFFF3`)

### Symptom:
Crash at a near-top address like `0xFFFFFE00` with register values containing heap garbage.

### Cause:
This is almost never a special hardware mirror. It indicates an uninitialized object pointer (the game tried to call `object->vtable[index]`, but `object` was zero or uninitialized memory). Usually caused by an earlier constructor failing or an unlifted library section (e.g. `XGRPH` or `DSOUND`) that failed to initialize.

### Fix:
Do not attempt to map memory at `0xFFFFFE00`. Instead:
1. Walk backward from the crash using `scripts/guest-stack.py`.
2. Trace what code allocated or initialized the pointer register using hardware watchpoints (`RECOMP_WATCH_WRITE=0x...`).
3. Ensure all XDK sections (`D3D`, `DSOUND`, `XPP`, etc.) were properly disassembled.

---

## 6. Guest Callstack: Scan vs Walk

### Trap:
The raw callstack printed during a VEH crash is an **unfiltered memory scan** of stack words that happen to fall within the code section. Because x86 functions often omit frame pointers (FPO), old return addresses from previously returned calls remain on the stack below `esp`.

### Solution:
Do not trust raw stack scans blindly. Use `scripts/guest-stack.py`, which correlates stack words against the exact list of return addresses generated by the lifter, ensuring that every printed frame represents a genuine, active call site.
