# Common Troubleshooting Patterns in Xbox Static Recompilation

This reference documents the most common failure modes and battle-tested solutions encountered when porting original Xbox games.

---

## 1. Unresolved Indirect Call (`[ICALL] Failed to resolve VA 0x...`)

### Symptom:
Console log prints:
```text
[ICALL] Failed to resolve VA 0x00201954 from caller sub_00123450
```
Followed by an immediate crash or null-pointer dereference.

### Cause:
The game called a function through a function pointer or C++ virtual method table (vtable). Static disassembly did not find a direct `CALL` instruction to this address, so the lifter never generated C code for it.

### Fix:
1. Extract the missing VA and add it to `config/seed_functions.json`:
   ```bash
   python -m tools.seed_from_log logs/run.log game/default.xbe \
       --functions tools/disasm/output/functions.json \
       --seeds config/seed_functions.json
   ```
2. Re-run `tools.disasm` with `--seed-functions config/seed_functions.json`.
3. Re-run `tools.func_id`, `tools.abi_analysis`, and `tools.recomp`.
4. Rebuild.

## 2. Audio Init Hang (DSP Command Doorbell)

### Symptom:
Game hangs at S2 during audio initialization. Watchdog triggers with thread spinning in DirectSound code.

### Cause:
Xbox DirectSound passes a command block to the DSP processor, sets a command bit, and spins until the DSP writes `0` back to indicate completion. In static recompilation, the DSP is not actively simulated by default.

### Fix:
Acknowledge the doorbell automatically in the APU hook:
- Identify the GP scratch memory page address (via `GPSADDR` scatter-gather table, usually offset `0x810`).
- Immediately clear the command word back to `0` upon receipt, or set environment variable:
  `RECOMP_APU_DSP_ACK=<address>`

## 3. GPU Pushbuffer Fence Spin (`D3DDevice_MakeSpace`)

### Symptom:
Game hangs with callstack inside `sub_XXXXXXXX` (D3D8 pushbuffer allocator), spinning on `Put - *GetPtr`.

### Cause:
Real NV2A hardware executes the pushbuffer in parallel and advances `*GetPtr`. In recompilation, pushbuffers are consumed synchronously at submit/flip time. If the game waits for `GetPtr` to move before writing more commands, it deadlocks.

### Fix:
Mirror the `Put` pointer into `*GetPtr` on every tick:
```c
xbox_Nv2aMirrorFence(g_pDevice_va, offset_Put, offset_GetPtr);
```

## 4. Arithmetic Errors / Silent Nan / Corrupted Logic (64-Bit Divides)

### Symptom:
Game does not crash, but calculations produce nonsensical results, matrices collapse to NaN, or timers jump wildly.

### Cause:
MSVC 64-bit integer divide helpers (`_alldiv`, `_aulldiv`, `_allrem`, `_aullrem`) rely on the x86 `rcr` (rotate through carry) instruction. If the lifter drops `rcr` or miscalculates multi-word shifts, operations where the divisor > $2^{32}$ fail silently.

### Fix:
- Add a runtime self-test in `main.c` (`recomp_selftest()`) that exercises the divide helpers with a 64-bit divisor ($0x100000007$) against known answers.
- If incorrect, override the math helper functions in `src/recomp_manual.c` with native C 64-bit integer arithmetic (`dividend / divisor`).

## 5. Corrupted Vtable / Wild Pointer at High VA (`0xFFFFFE00` or `0xFFFFFFF3`)

### Symptom:
Crash at a near-top address like `0xFFFFFE00` with register values containing heap garbage.

### Cause:
This is almost never a special hardware mirror. It indicates an uninitialized object pointer (the game tried to call `object->vtable[index]`, but `object` was zero or uninitialized memory). Usually caused by an earlier constructor failing or an unlifted library section (e.g. `XGRPH` or `DSOUND`) that failed to initialize.

### Fix:
Do not attempt to map memory at `0xFFFFFE00`. Instead:
1. Walk backward from the crash using `scripts/guest-stack.py`.
2. Trace what code allocated or initialized the pointer register using hardware watchpoints (`RECOMP_WATCH_WRITE=0x...`).
3. Ensure all XDK sections (`D3D`, `DSOUND`, `XPP`, etc.) were properly disassembled.

## 6. Guest Callstack: Scan vs Walk

### Trap:
The raw callstack printed during a VEH crash is an **unfiltered memory scan** of stack words that happen to fall within the code section. Because x86 functions often omit frame pointers (FPO), old return addresses from previously returned calls remain on the stack below `esp`.

### Solution:
Do not trust raw stack scans blindly. Use `scripts/guest-stack.py`, which correlates stack words against the exact list of return addresses generated by the lifter, ensuring that every printed frame represents a genuine, active call site.

## 7. MSVC C11 Atomics `#error: "C atomic support is not enabled"`

### Symptom:
When compiling runtime C files on Windows using MSVC:
```text
C:\Program Files\Microsoft Visual Studio\...\include\vcruntime_c11_stdatomic.h(12,1): error C1189: #error: "C atomic support is not enabled"
```

### Cause:
By default, the MSVC C compiler does not enable C11/C17 atomic primitives when `<stdatomic.h>` is included.

### Fix:
In CMake, pass the `/experimental:c11atomics` compiler switch to all C source files on MSVC:
```cmake
if(MSVC)
    get_target_property(_all_target_sources ${target} SOURCES)
    foreach(_src IN LISTS _all_target_sources)
        if(_src MATCHES "\\.c$")
            set_property(SOURCE ${_src} APPEND PROPERTY COMPILE_OPTIONS /experimental:c11atomics)
        endif()
    endforeach()
endif()
```
Or for newer MSVC versions with C11/C17 standard enabled:
```cmake
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
```

## 8. Compiler-Specific GCC/Clang Atomics on MSVC (`__ATOMIC_RELEASE` undeclared)

### Symptom:
Compiling cross-platform renderer or runtime sources fails under MSVC:
```text
error C2065: '__ATOMIC_RELEASE': undeclared identifier
error C2065: '__ATOMIC_ACQUIRE': undeclared identifier
error C3861: '__atomic_store_n': identifier not found
```

### Cause:
The code relies on GCC/Clang built-in atomic intrinsics (`__atomic_store_n`, `__atomic_load_n`, `__ATOMIC_RELEASE`) which do not exist in the Microsoft Visual C++ compiler (`cl.exe`).

### Fix:
Add a Windows/MSVC portability guard using Win32 Interlocked functions or standard C11 atomics:
```c
static void atomic_state_store(int value) {
#if defined(_WIN32)
    InterlockedExchange((volatile LONG*)&s_state, (LONG)value);
#else
    __atomic_store_n(&s_state, value, __ATOMIC_RELEASE);
#endif
}

static int atomic_state_load(void) {
#if defined(_WIN32)
    return (int)InterlockedCompareExchange((volatile LONG*)&s_state, 0, 0);
#else
    return __atomic_load_n(&s_state, __ATOMIC_ACQUIRE);
#endif
}
```

## 9. C++17 Lambda Constant Evaluation Trap (`error C2131`)

### Symptom:
When compiling host C++ runtime code containing `static_assert` inside a lambda:
```text
error C2131: expression did not evaluate to a constant
failure was caused by reading a value that is unknown during constant evaluation
```

### Cause:
Under MSVC strict C++17 mode, evaluating an outer enclosing function's `constexpr` local variable within a `static_assert` inside a lambda closure is rejected because the compiler treats it as reading an outer variable context during constant evaluation.

### Fix:
1. Re-declare the `constexpr` directly within the lambda closure body, or
2. Use compile-time boolean literals or template constants:
```cpp
auto start_session = [&](bool netplay) -> bool {
    // WRONG (under MSVC C++17): static_assert(!outer_flag, "...");
    // RIGHT: Localize or evaluate constant directly
    constexpr bool local_flag = false;
    static_assert(!local_flag, "restore only when feature is mod-owned");
    ...
};
```

## 10. Paths With Spaces in Sub-Toolchain Invocations

### Symptom:
Recompilation CLI or sub-tool fails with truncated path errors, e.g.:
```text
FATAL: config file not found: C:\Project\Harvest
```
When the actual project path is `C:\Project\Harvest Moon - Back to Nature (USA)`.

### Cause:
Toolchain CLI scripts execute subprocesses (`psxrecomp-bios.exe`, `xbe_parser`, etc.) without wrapping path arguments in double quotes.

### Fix:
1. In CLI process runners (Python / PowerShell / Shell), always pass subprocess arguments as a list of strings (e.g. `subprocess.run([tool_exe, "--config", config_path])`) rather than string concatenation with `shell=True`.
2. When calling tools from shell scripts, quote all variable expansions: `"$CONFIG_PATH"`.
3. If using precompiled third-party binaries that have this defect, invoke the tool from inside the target directory using relative paths:
   ```powershell
   Set-Location "recomp_project"
   & "..\tools\psxrecomp-cli\libexec\tool.exe" --config "psxrecomp\bios\OpenBIOS.toml"
   ```

## 11. Massive Code Generation & Compiler Heap Overflow (Split-TU Strategy)

### Symptom:
Compiler runs out of memory (`fatal error C1002: compiler is out of heap space in pass 2`) or produces an un-linkable `.obj` file exceeding object file size limits.

### Cause:
A complete console game generates between 500,000 and 1,500,000+ lines of C code. Emitting this into a single monolithic file overwhelms compiler AST caches and prevents multi-threaded parallel compilation.

### Fix:
1. **Sharding (Split Translation Units):**
   Always shard recompiled functions across 10 to 20 separate C translation units (`recomp_full_00.c` ... `recomp_full_19.c`), targeting ~1,000 to 2,000 functions or ~35,000 lines per file.
2. **Global Dispatch Table (`recomp_dispatch.c`):**
   Keep all function prototypes in a shared header (`recomp_decls.h`) and emit an indexed flat dispatch table in a dedicated dispatch C file.
3. **Compiler Flags:**
   Ensure `/bigobj` is enabled on MSVC to support extended section headers (>65,536 sections per translation unit).
4. **Parallel Build:**
   With split TUs, compile with `cmake --build build --config Release --parallel` to fully utilize all CPU cores.
